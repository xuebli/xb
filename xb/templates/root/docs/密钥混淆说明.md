# 密钥混淆说明（防围观，非加密）

secrets.yaml 里的敏感值（飞书 app_secret 等）落盘时是 `obf1:` 前缀的混淆密文，
不是明文。本文说明机制、判断规则与使用方式。

---

## 一句话

**键名含 secret / password / token 的值，写入 secrets.yaml 时自动混淆成
`obf1:<base64>`；读取时后端透明解密，业务代码无感知。**

## 判断规则

唯一规则在 `backend/managers/secret_obfuscator.py`：

```python
SENSITIVE_TAGS = ("secret", "password", "token")   # 键名包含即混淆，大小写不敏感
```

| 键示例 | 混淆 | 原因 |
|---|---|---|
| `feishu.app_secret` | ✓ | 含 secret |
| `leo_daemon.password` | ✓ | 含 password |
| `mqtt.token` | ✓ | 含 token |
| `feishu.app_id` | ✗ | 半公开标识，不含敏感词 |
| `feishu.update_folder_url` | ✗ | 只是链接 |

已有 `obf1:` 前缀的值跳过（不重复混淆）；空值跳过。
新增敏感配置时只要键名带上这三个词之一就自动被覆盖。

## 触发时机（不分开发/打包态）

1. **后端启动时兜底**：扫一遍 secrets.yaml，明文敏感键就地转密文；
2. **设置页保存时**：写入后立即混淆，不等下次启动。

混淆前自动留 `secrets.yaml.bak` 备份，再原子替换，不会丢原文。

## 读取链路

```
secrets.yaml: obf1:PSkq...
        │
        ▼  path_manager.get_config_value() 检测到 obf1: 前缀 → 透明解密
业务代码拿到明文（调飞书 API 等）——程序必须用明文，这是"混淆≠加密"的根本原因
```

## 设置页表现

- 密钥字段渲染为密码框，显示**与明文等长的圆点**（真实值不下发前端）；
- 圆点原样保存 = 不修改；删掉圆点输新值 = 修改；
- 小眼睛 👁 查看的是**落盘原文**（即 `obf1:` 密文），用于确认"确实混淆了"，
  全程不解密；
- 密钥框默认只读（防浏览器自动填充顶掉圆点），点击后才可编辑。

## 手动转换

```bash
cd backend
python -m managers.secret_obfuscator <明文>           # 输出 obf1: 密文
python -m managers.secret_obfuscator --file <yaml>    # 就地混淆文件中的明文敏感键
# 还原（调试时确认内容用）：
python -c "from managers.secret_obfuscator import deobfuscate; print(deobfuscate('obf1:...'))"
```

## 诚实边界（重要）

**这是防围观，不是加密。** 算法是 XOR + Base64，混淆密钥内置在
`secret_obfuscator.py` 里并随安装包分发——拿到应用文件的人两步就能还原明文。

防得住：配置文件被截图/围观/git 误提交、磁盘明文扫描。
防不住：拿到你电脑或安装包的有心人。

真正的闸门是访问控制（本机判定 / 飞书登录），不是这层混淆。
若需更强保护，方向是 OS 密钥环（Windows DPAPI / Linux Secret Service）
或服务端托管密钥，详见项目讨论记录——内网工具场景一般不值得。
